# Strict Go statement coverage admits measured built-in reports and fingerprinted cache evidence

## Context and Problem Statement

For #23 strict Go statement coverage, existing or explicit raw profiles have no proof that they describe current source and test inputs. Recommended first slice: reject --coverage-report and --use-existing-coverage in strict Go run as usage conflicts, including raw reports generated by --coverage-command; retain their current non-strict behavior. Built-in own/all-tests and configured listed coverage are admitted only when measurement succeeds now or matching independent cached evidence exists. Do not bless old reports by attaching current hashes. Fingerprint the actual coverage producer/options and conservative nearest-module Go source/test inventory, including build-tagged files, excluding nested modules, plus module go.mod/go.sum, project config and support matches; record relevant Go build environment. Changes, additions or removals stale the independent evidence. Opaque harness/external inputs require configured support and are not inferred. This keeps the first slice bounded but removes raw-profile workflows from strict mode. Choose (a) this built-in-only strict admission and conservative fingerprint rule, or (b) design an attested profile/sidecar format so strict mode can accept external or existing reports.

Asked as q-26, about uncovered-statements.

## Considered Options

- Built-in and listed measurement with conservative fingerprints; reject unattested raw profiles
- Design attested profile sidecars for external and existing reports

## Decision Outcome

Choose (a), built-in-only strict Go coverage admission. Strict Go run rejects raw --coverage-report, --use-existing-coverage and --coverage-command workflows rather than attaching current hashes to unattested profiles. Admit successful built-in/listed measurement and matching independent cached evidence. Fingerprint the recorded coverage producer/options, module Go source/test inventory (including build-tagged files, excluding nested modules), go.mod/go.sum, project config/support matches and relevant Go build environment. Compare additions, removals and edits. Opaque harness/external inputs require configured support and are not inferred. Non-strict and other-language report behavior remains unchanged.

### Consequences

Freshness belongs to the recorded coverage producer, not to the mutation outcome scope. Module production-source changes can stale statement coverage even if the judged function hash is unchanged. Strict Go commands reject --coverage-report, --use-existing-coverage and --coverage-command workflows; non-strict commands and other languages retain them. Matching independent cache evidence may be reused without measuring again, including evidence from a broader recorded suite. Failed, partial or unrelated-module measurement cannot prove a selected function covered. Future external-report support needs an attestation contract rather than current hashes pasted onto an old profile. Configured support declares opaque inputs; the tool does not infer arbitrary external inputs.
